# 一期技术架构方案：轻量、可扩展的制造 ERP

## 1. 架构结论

一期推荐采用**模块化单体 + 关系型数据库 + 响应式 Web/PWA**。它比微服务更轻，部署、调试和事务一致性都更直接，尤其适合当前单公司、单仓库、无外部集成的阶段；同时通过清晰模块边界、API 契约和领域事件，为后续多仓、多组织、WMS/MES/财务集成保留扩展路径。

不建议一期采用微服务、原生双端 App、复杂工作流引擎、消息队列集群或独立数据仓库。这些组件当前无法形成足够业务收益，反而增加部署与运维成本。

## 2. 推荐技术选型

| 层级 | 推荐 | 原因 |
| --- | --- | --- |
| 前端 | React + TypeScript + Vite + Ant Design + TanStack Query | 企业表单、表格和权限页面成熟；开发节奏快、生态稳定。 |
| 移动端 | 同一套 React 响应式界面 + PWA | 复用业务代码，支持手机浏览器、摄像头扫码、拍照和安装到桌面。 |
| 后端 | NestJS + TypeScript | 模块化、依赖注入、验证、权限和 OpenAPI 支持完善；前后端语言统一。 |
| ORM/数据访问 | Prisma 或 Drizzle ORM，关键库存操作保留显式事务 SQL | 常规开发速度快；关键账务操作可精确控制事务、锁与幂等。 |
| 主数据库 | PostgreSQL | 强事务、行锁、JSONB、全文检索、备份与扩展能力均适合 ERP。 |
| 缓存与任务 | Redis + BullMQ | 缓存、短期锁、文件解析、报表导出等异步任务足够轻量。 |
| 文件存储 | S3 兼容对象存储（MinIO 起步） | 适合图片、XLSX、解析附件与审计留档；可从本地部署平滑迁移到云存储。 |
| 图片/XLSX 解析 | XLSX 结构化解析 + OCR/视觉模型异步任务 | XLSX 用确定性字段映射；图片先 OCR，再由模型归一化为候选字段。 |
| 部署 | Docker Compose：Web、API、Worker、PostgreSQL、Redis、MinIO、反向代理 | 单机/单云主机即可部署，环境可复制，后续可迁移容器平台。 |
| 可观测性 | 结构化日志 + Sentry + 健康检查 + PostgreSQL 备份任务 | 首期以低运维成本获得错误定位与恢复能力。 |

## 3. 系统结构

```text
PC 浏览器 / 手机 PWA
          |
          v
      反向代理与 HTTPS
          |
          v
       ERP Web 前端
          |
          v
      ERP API（模块化单体）
  ┌───────┼───────────┬─────────┐
  v       v           v         v
权限主数据  采购销售库存生产  文件解析任务  报表查询
  |       |           |         |
  └───────┴─────┬─────┴─────────┘
                v
           PostgreSQL
             |       |
             v       v
           Redis    对象存储
                    图片/XLSX/附件
```

前端只通过 API 访问业务数据。解析与导出通过 Worker 异步执行，避免用户上传大文件时阻塞库存与生产事务。

## 4. 后端模块边界

| 模块 | 责任 | 禁止直接依赖 |
| --- | --- | --- |
| 身份与权限 | 登录、用户、角色、数据范围、配方权限、审计 | 不直接修改业务单据 |
| 主数据 | 物料、单位、客户、供应商、币种税率、BOM | 不直接写库存余额 |
| 采购 | 采购单、采购入库、采购退货 | 不绕过库存模块处理入库 |
| 销售 | 订单、发货、退货、库存锁定 | 不绕过库存模块处理出库 |
| 生产 | 生产订单、领退料、完工、损耗、配方快照 | 不直接改库存余额或成本 |
| 库存 | 库存事务、批次、库存余额、锁定、盘点、调拨 | 只接受已验证的业务命令 |
| 成本 | 移动加权、库存成本、生产订单成本 | 不负责业务单据状态流转 |
| 文件智能化 | 上传、OCR/XLSX 解析、字段匹配、草稿生成 | 不可直接过账业务单据 |
| 报表 | 读模型、聚合查询、导出 | 不写交易数据 |

模块之间通过应用服务和明确 DTO 调用；库存过账完成后发布内部领域事件，例如 `InventoryPosted`、`ProductionCompleted`。一期事件可保存在数据库事务内的 outbox 表，再由 Worker 消费，避免引入独立消息中间件。

## 5. 关键技术规则

### 5.1 库存与成本一致性

- 库存余额不是可自由编辑的字段，只能由库存事务追加并汇总得出。
- 每个过账命令都必须携带幂等键；同一请求重试不得重复扣减或增加库存。
- 批次扣减、库存锁定、库存余额更新和成本记录在同一 PostgreSQL 事务中提交。
- 对同一物料/批次余额使用行级锁或乐观版本号控制并发，防止多手机同时扫码造成超领/超发。
- 过账后使用冲销事务纠错，保留原始单据与关联关系。

### 5.2 多币种与多税率

- 公司只定义一个本位币；采购和销售单据保存交易币种、交易金额、汇率、汇率日期、本位币金额与税额。
- 汇率作为主数据版本化保存，业务单据提交后锁定实际使用汇率，后续汇率变动不回写历史单据。
- 税率按单据行存储，避免修改税率主数据影响历史金额。

### 5.3 配方保密

- BOM 明细 API、导出任务、附件下载、搜索索引均在服务端校验配方权限，前端隐藏不是安全控制。
- 生产任务 API 只返回操作员完成任务所需的指令数据，不返回完整配方百分比与成本。
- 对配方查看、导出、修改建立专门审计事件，保留操作者、时间、来源 IP/设备和对象版本。

### 5.4 文件解析

```text
上传原文件 -> 病毒/格式检查 -> 对象存储 -> 异步解析 -> 字段候选与置信度
-> 人工映射物料/客户/供应商 -> 生成草稿 -> 用户提交 -> 正常过账流程
```

- XLSX 优先采用模板和字段映射，结果可预测、成本低。
- 图片通过 OCR 提取文本，再转换为标准字段；解析服务只产生候选值，绝不直接创建已过账单据。
- 原文件采用私有对象存储，访问经过业务权限校验，并保留文件哈希、解析版本和关联单据。

## 6. 数据库设计原则

- 业务表统一带 `id`、`company_id`、`status`、`version`、创建/更新时间和创建/更新人；即使一期单公司也保留 `company_id`，避免未来重构。
- 金额与数量使用 PostgreSQL `numeric`，不使用浮点数。
- 关键交易表包括单据头/行、批次、库存事务、库存余额、库存锁定、成本记录、BOM 版本、审计日志、文件与解析任务。
- 对高频查询建立组合索引：`物料+仓库+批次`、`到期日期+库存状态`、`单据类型+单据号`、`来源单据`、`生产订单`。
- 审计和库存事务采用只追加策略；历史归档按时间分区或冷存储演进，不在一期过早分库分表。

## 7. API 与前端原则

- 所有命令型 API（提交、过账、冲销、批次锁定）使用明确动作端点与幂等键；不使用通用更新接口修改关键状态。
- 生成 OpenAPI 文档，前端从契约生成类型，减少字段不一致。
- 表单支持草稿自动保存、服务端字段校验、附件关联、操作日志和失败提示。
- 手机端使用同一 API；关键按钮具备防重复提交、网络重试提示和扫码后即时校验。
- PWA 只缓存静态资源和允许离线查看的非敏感内容；库存过账与生产领料必须在线执行，避免离线冲突。

## 8. 部署、备份与安全基线

- 初期可在一台 Linux 云主机或本地服务器上以 Docker Compose 部署；生产环境使用 HTTPS、私有网络和受限管理端口。
- PostgreSQL 每日全量备份加持续归档，附件对象存储开启版本与生命周期策略；每季度执行一次恢复演练。
- 访问令牌短时有效，密码使用强哈希；生产密钥通过部署环境注入，不写入代码或镜像。
- 配置请求限流、上传大小与格式白名单、病毒扫描接口预留、审计日志只追加。
- 监控 API 错误率、过账失败、Worker 队列积压、磁盘空间、备份结果和数据库连接数。

## 9. 可扩展路径

| 未来需求 | 一期预留方式 | 后续扩展 |
| --- | --- | --- |
| 多仓/多公司 | 全局主键、公司维度、仓库/库位模型 | 增加数据范围与跨组织结算，不改库存事务模型 |
| 财务对接 | 单据、成本、币种税率和 outbox 事件 | 新增财务适配器和凭证模块 |
| WMS/MES | 业务命令 API、库存事件、批次模型 | 对接扫码设备、工序报工、设备数据 |
| 高并发/多团队 | 模块边界、独立 Worker、读写分离预留 | 先拆文件解析/报表，再按负载拆库存外围模块 |
| 原生移动 App | 稳定 API、响应式业务模型 | 以 API 接入 Flutter/React Native，不重写后端 |

## 10. 实施建议

1. 先完成领域数据字典、单据状态机、库存事务类型和配方权限矩阵，再开始原型或代码。
2. 开发顺序建议为：身份权限与主数据 -> 库存/批次底座 -> 采购销售 -> BOM/生产 -> 成本与报表 -> 文件解析 -> PWA 优化。
3. 每完成一个库存业务动作，就补充对应的并发、重复提交、冲销、权限和追溯测试；库存正确性优先于页面数量。
4. 在拿到真实采购单、发货单、订单和财务流水样例后，再锁定 XLSX 模板与图片解析字段，不应先假设文档格式。
